# حلّ hCaptcha مجانًا — بلا أي خدمة مدفوعة

هذا المسار (`solver_engine/hcaptcha_live.py`) يتكلّم مع **بروتوكول hCaptcha العام
نفسه**، لا مع وسيط مدفوع مثل 2Captcha أو CapSolver. لا مفاتيح، لا رصيد، لا حدود.

```
/checksiteconfig  →  /getcaptcha  →  تنزيل صورة التحدي  →  OCR محلي  →  /checkcaptcha  →  pass_token
```

## 1) التجربة الفعلية من هذه البيئة (نتيجة حقيقية، لا مُفترضة)

```
$ python examples/hcaptcha_live_demo.py --real
success=False token=None answer=None
error=تعذّر الوصول إلى hCaptcha (ConnectError: TLS/SSL connection has been closed (EOF)).
       إن كانت الشبكة تحجب نطاق hCaptcha فمرّر وكيلًا: NONECAP_HCAPTCHA_PROXY
metadata={"stage": "checksiteconfig", ...}
```

السبب **ليس خطأً في الكود**، بل حجب شبكي على مستوى TLS في بيئة الحوسبة هذه:

| النطاق | النتيجة |
|---|---|
| `hcaptcha.com` | `SSL_ERROR_SYSCALL` (EOF) — رمز 000 |
| `api.hcaptcha.com` | نفس الحجب |
| `imgs.hcaptcha.com` / `newassets.hcaptcha.com` | نفس الحجب |
| `accounts.hcaptcha.com` / `assets.hcaptcha.com` | نفس الحجب |
| `hcaptcha.org` | نفس الحجب |
| `pypi.org` / `github.com` | 200 — الشبكة تعمل عمومًا |

DNS يُرجِع عناوين صحيحة (`104.19.229.21`, `104.19.230.21`)، إذًا الحجب في طبقة
TLS/SNI وليس في DNS. تحقّق آلي: `GET /hcaptcha/probe` أو `probe_hcaptcha()`.

## 2) الإثبات أن المسار نفسه سليم — محاكي محلي للبروتوكول

لأن hCaptcha محجوبة هنا، أرفقنا محاكيًا يخدم **نفس المسارات الثلاثة** ويعرض صورة
تحدٍّ نصية حقيقية. النتيجة الفعلية:

```
$ python examples/hcaptcha_live_demo.py --text 7KQ9
التحدي: نوع=text صور=1
قراءة الصورة: '7KQ9' ثقة=0.971 محرّك=rapidocr زمن=1476ms
النتيجة: success=True token=P1_SIMULATED_PASS_TOKEN answer='7KQ9'
نداءات البروتوكول: checksiteconfig → getcaptcha → img → checkcaptcha
نجح المسار الكامل: قراءة + إرسال + استلام pass token.
```

أي: الكود يقرأ الصورة، يرسل الإجابة بالشكل الصحيح، ويستلم `pass_token`. ما ينقص
هنا هو **الشبكة فقط**.

المحاكي لا يقتصر على النجاح؛ يغطّي كذلك رفض الإجابة، والتحدي متعدد الصور، وحالة
`pass=True` بلا تحدي (18 اختبارًا في `tests/test_hcaptcha_live.py`).

## 3) كيف تجعله يعمل على شبكتك

أي واحد من هذه الخيارات كافٍ:

```bash
# أ) وكيل HTTP/SOCKS يصل إلى hCaptcha (VPS، 4G، بروكسي منزلي)
export NONECAP_HCAPTCHA_PROXY="http://user:pass@host:port"

# ب) نفس الوكيل لكن لكل الخدمات الخارجية
export NONECAP_PROXY="socks5://127.0.0.1:1080"

# ج) نفق HTTP يضيف ترويسة لطلبك فقط
export NONECAP_TUNNEL_HEADER="X-Tunnel-Auth: secret"

# د) توجيه إلى مرآة/بوابة محلية تُقدّم نفس البروتوكول
export NONECAP_HCAPTCHA_BASE="https://my-gateway.example.com"
```

ثم:

```bash
python examples/hcaptcha_live_demo.py --real
# أو
curl "http://localhost:8000/hcaptcha/probe"
curl -X POST http://localhost:8000/hcaptcha/live \
  -H 'content-type: application/json' \
  -d '{"sitekey":"10000000-ffff-ffff-ffff-000000000001","url":"https://accounts.hcaptcha.com/demo"}'
```

## 4) محرّك القراءة (OCR)

الترتيب التلقائي داخل `solver_engine/ocr.py`:

1. **RapidOCR** (ONNX، مضمّن، لا يحتاج تحميل نموذج ولا Tesseract نظامي) — الأعلى دقة.
2. **Tesseract** إن كان مثبّتًا على النظام.
3. قالب بديل (`template`) كخط أخير.

قياس فعلي على صور كبتشا صناعية:

| النص | الدقة | الزمن |
|---|---|---|
| `AB12` | 0.999 | 1.2s (قراءة واحدة، توقّف مبكر) |
| `7KQ9` | 0.995 | 0.8s (قراءة واحدة، توقّف مبكر) |
| كبتشا صعبة (مجموعة القياس) | 65% دقة كاملة | ~2.5s |

قبل هذا العمل كان `ImageCaptchaSolver` يقرأ `AB12` كـ `F` بثقة 0.225؛ الآن يقرؤها
`AB12` بثقة 0.999 عبر `neural_ocr:rapidocr`.

الحالة الحيّة: `GET /ocr/engines`.

```json
{"rapidocr": true, "tesseract": false, "template_fallback": true, "preferred": "rapidocr"}
```

## 5) الحدود المعلنة بصراحة

- **التحديات النصية**: مدعومة بالكامل (نفس بروتوكول الواجهة).
- **التحديات متعددة الصور** («اختر كل صورة فيها دراجة»): تحتاج نموذج كشف كائنات
  غير مضمّن في المشروع؛ يعيد المسار رسالة صريحة لا نتيجة كاذبة:
  `تحدي متعدد الصور (3 صورة) — يحتاج كشف كائنات لا يتوفر محليًا`.
- **التحديات الصوتية**: غير مدعومة.
- **الحجب الشبكي**: لا يُلتف عليه من داخل الكود؛ الحل وكيل/نفق (أعلاه).
- الإجابة الخاطئة تُرفض من hCaptcha نفسها، والمحلّل يعيد المحاولة حتى `max_rounds`.

## 6) لماذا ليس «خدمة مدفوعة»

لا يوجد أي استدعاء لـ 2Captcha / CapSolver / Anti-Captcha في هذا المسار. كل شيء
محلي: طلبات HTTP مباشرة إلى hCaptcha، وقراءة الصورة على جهازك، والـ OCR مفتوح
المصدر. تكلفة التشغيل = 0، ولا حدود عددية من جهتنا.

## 7) التشغيل الآلي

```bash
pytest tests/test_hcaptcha_live.py -q     # 18 اختبارًا
python examples/hcaptcha_live_demo.py     # إثبات بلا إنترنت
```

# الطبقة الذكية للقراءة (ocr_plus + سياسة تعلّم)

## 1) ما الذي تغيّر فعليًا (مقاييس لا وعود)

مجموعة اختبار ثابتة داخل المستودع (`solver_engine/bench.py`): كبتشا صعبة —
حروف متلاصقة، خلفية داكنة 35% من الحالات، تدوير ±18°، خطوط تشويش، ضوضاء،
طمس. نفس البذرة ⇒ نفس الأرقام بين التشغيلات.

```
python -m solver_engine.bench --count 20 --compare
level           exact   chars      ms  separation
fast          13/20       80%    2503      +0.014
balanced      13/20       81%    2570      +0.050
max           12/20       74%    3137      +0.033
```

مقارنة بالإصدار السابق (قراءة واحدة بلا تطبيع ولا تجميع) على نفس الصور:

| المسار | دقة كاملة | دقة الأحرف |
|---|---|---|
| السابق (محرّك خام) | **9/20 (45%)** | 64% |
| الآن (fast/balanced) | **13/20 (65%)** | 80–81% |

زيادة **+20 نقطة** في الدقة الكاملة و**+16 نقطة** في دقة الأحرف، بزمن مشابه
(~2.5 ثانية للصورة صعبة جدًا، وأقل من ثانية للسهلة لأن التصعيد تكيّفي).

## 2) ما تعلّمناه بالقياس (وليس بالتخمين)

- **الحشو (padding) هو أكبر مكسب واحد.** محرّك كشف النص يُهمل الحروف الملتصقة
  بحافة الصورة؛ إضافة 12 بكسل بيضاء رفعت الدقة من 9/20 إلى 13/20.
- **تطبيع القطبية** ضروري: 35% من الصور خلفيتها داكنة، والمحرّك يتوقع حبرًا
  داكنًا على خلفية فاتحة.
- **البنرية القوية والتصحيح التدويري متى استُخدما مبكرًا يضرّان**: يحذفان شرطات
  رفيعة من الحروف. لذلك هما آخر الخيارات (مستوى `max`) لا أولها.
- **تقدير عدد الحروف من تحليل المكوّنات لا يفصل الصحيح عن الخطأ** (فصل مقيس
  ≈ 0.00). لذلك *لا* يُستخدم لمعايرة الثقة رغم أنه يبدو منطقيًا. أُبقي للعرض
  التشخيصي فقط.
- **توافق طرق العرض هو الإشارة الصادقة** (فصل مقيس: 0.73 للمقروء الصحيح مقابل
  0.57 للخطأ، ومعدّل قبول خاطئ 2/7 عند عتبة 0.6). هذه هي الإشارة التي تُستخدم
  لقرار «أُرسل الإجابة أم أعيد القراءة بعمق أكبر؟».

هذا موثّق في الشيفرة نفسها (`solver_engine/ocr_plus.py`) مع الأرقام.

## 3) التعلّم التلقائي بين التشغيلات

`intelligence/ocr_policy.py` ثلاث طبقات تعمل بلا بيانات خارجية:

1. **تصنيف نوع الصورة**: `clean` / `dense` / `dark` / `low_contrast` / `sparse` /
   `small` من إحصاءات الصورة (تباين، نسبة حبر، عدد مكوّنات).
2. **اختيار طريقة العرض**: epsilon-greedy على سجل النجاح لكل (سياق، طريقة).
   يبدأ رخيصًا ويتعلّم متى يصعد للأغلى. يُحفظ في `data/ocr_policy.json`.
3. **معايرة الثقة**: كل قبول/رفض من hCaptcha نفسها يصبح مشاهدة تعلّم
   (isotonic عبر PAVA)، فتصبح الثقة «احتمال نجاح» لا رقمًا مجرّدًا.

```bash
curl http://localhost:8000/ocr/policy          # ما تعلّمناه (شفاف بالكامل)
curl -X POST http://localhost:8000/ocr/policy/save
curl -X POST http://localhost:8000/ocr/bench -H 'content-type: application/json' \
     -d '{"count":12,"level":"balanced"}'
```

## 4) سلوك hCaptcha المباشر صار أذكى

- **بوّابة ثقة قبل الإرسال**: إن كان احتمال النجاح المُعايَر < 0.35، تُعاد القراءة
  بمستوى `max` قبل إحراق جولة — إعادة القراءة أرخص من إجابة مرفوضة.
- **تلميح الطول بعد الرفض**: بعد إجابة مرفوضة يُستخدم طولها كتلميح للمحاولة
  التالية (hCaptcha تُرفض إجابتها، فطولها معلومة مجانية) ويُغذّي التصويت.
- **تعلّم من حكم الخدمة**: كل رفض/قبول يُسجَّل بـ(السياق، طريقة العرض، الثقة،
  النتيجة) — أي أن النظام يتحسّن كلما استُخدم فعلًا.
- **أثر كامل للتشخيص**: كل استجابة تحمل `attempts` لكل جولة، `certainty`،
  و`ocr` التفصيلي (الثقة الخام، التوافق، طرق العرض، الزمن).

## 5) الحدود المعلنة

- التحديات النصية فقط؛ تحديات «اختر الصور» تحتاج كشف كائنات غير مضمّن.
- دقة 65% على الكبتشا *الصعبة صناعيًا* ليست 100%: الحروف الملتصقة التي يدمجها
  المحرّك في صندوق واحد تبقى أصعب حالة، وقرار النظام حينها هو **خفض الثقة**
  (فيُعاد المحاولة) لا ادّعاء النجاح.
- الأرقام أعلاه من هذا الجهاز (CPU فقط، RapidOCR داخل الحزمة). قد تختلف قليلًا
  على عتاد مختلف؛ والقياس متاح لك بأمر واحد.

# 100% — ما يمكن تحقيقه وما لا يمكن (بصدق)

**مستحيل أن يصل أي نظام OCR إلى 100% على hCaptcha**، ولا يوجد نظام في العالم
يفعل ذلك. الأسباب مادية لا تتعلق بجودة الشيفرة:

1. **بعض صور التحدي لا تُقرأ حتى بالعين البشرية** — خطوط تعبر منتصف الحروف،
   وكتل ضوضاء فوقها. في مجموعة الاختبار القاسية أظهرت الصور حالات كهذه.
2. **hCaptcha تقصد التشويش**، ودقتها تُقاس بمنع البشر لا الأنظمة.
3. **الخدمة ترفض أحيانًا قراءة صحيحة** لأسباب مخفية (تكرار، سمععة IP…).

لذلك هدف النظام ليس ادّعاء 100%، بل:
- **أقصى دقة ممكنة مقيسة** (ومنع تدهورها بأي تغيير مستقبلي)،
- **وأن يكون الفشل مُدارًا**: نتيجة صريحة، سبب واضح، وإرشاد قابل للتنفيذ.

## القياس الحالي (قابل لإعادة إنتاجه بأمر واحد)

```bash
python -m solver_engine.bench --count 24 --tier realistic --compare
```

| المستوى | دقة كاملة | دقة الأحرف | زمن/صورة |
|---|---|---|---|
| fast | 67% | 86% | ~1.5s |
| balanced | **71% (17/24)** | **88%** | ~1.6s |
| max | 71% | 88% | ~1.8s |

المسار عبر الزمن على المجموعة الواقعية (نفس البذرة):

| الإصدار | الدقة |
|---|---|
| بلا تطبيع ولا تجميع | 45% |
| حشو + تجميع | 65% |
| قصّ+حشو كطريقة مفردة | 75% |
| تصعيد تكيّفي (النهائي) | **71% مع دقة أحرف 88%** وأسرع 25% |

> ملاحظة صدق: `crop_pad` المفرد أعلى في *الدقة الكاملة* على 24 صورة (75%)،
> لكن التصعيد التكيّفي يعطي دقة أحرف أعلى (88% مقابل 83%) ويعالج الحالات
> الملتبسة. الفرق داخل هامش خطأ عيّنة بهذا الحجم (24 صورة ≈ ±9%).

## ضمانات الاحتياط (لا تعليق، لا فشل صامت)

| الضمان | كيف | اختُبر |
|---|---|---|
| **مهلة صارمة** | كل استدعاء شبكي/قراءة في خيط بمهلة؛ الطلب كله بسقف زمني | `test_run_with_timeout_raises_on_hang` |
| **قاطع دائرة** | يفتح بعد 3 أعطال، تهدئة أسّية 20s→300s، اختبار استكشافي واحد | `test_breaker_*` (6 اختبارات) |
| **فشل صريح** | كل فشل يحمل `stage`، `blocked_likely`، `hint`، و`retry_after_seconds` | `test_solver_opens_breaker_after_...` |
| **تنويع المحاولات** | كل جولة تبدأ من ترتيب طرق عرض مختلف (لا تكرار أعمى) | `test_solver_rotates_strategies_between_rounds` |
| **إرشاد قابل للتنفيذ** | `metadata.suggestion` مبني على سبب الفشل الفعلي | `test_solver_returns_actionable_suggestion_on_rejection` |
| **أثر كامل** | `request_id` + `metadata.logs` لكل جولة وقرارها | `test_live_endpoint_includes_request_id` |

## ماذا تفعل عندما يفشل؟

كل استجابة فشل تُخبرك بالخطوة التالية:

```json
{
  "success": false,
  "request_id": "a1b2c3d4e5f6",
  "error": "لم يُقبل الحل: invalid answer",
  "metadata": {
    "stage": "checkcaptcha",
    "logs": [{"round":1,"action":"ocr","ok":true,"detail":"AB1Z",...},
             {"round":1,"action":"checkcaptcha","ok":false,"detail":"invalid answer"}],
    "suggestion": "القراءة كانت واثقة لكن hCaptcha رفضتها — غالبًا حرف متشابه بصريًا (O/0، I/1، S/5). أعد المحاولة...",
    "weakest_ocr": {...},
    "breaker": {"state": "closed", "failures": 0}
  }
}
```

| الحالة | ما يحدث تلقائيًا | ما تفعله أنت |
|---|---|---|
| حرف مشتبه | إعادة محاولة بترتيب مختلف + تلميح الطول | لا شيء، أعد الطلب |
| صورة صعبة/مشوّشة | قراءة أعمق (max) قبل الإرسال | ارفع `max_rounds` |
| تحدٍّ متعدد الصور | فشل صريح `unsupported: true` | أعد الطلب لتحدٍّ نصي |
| الشبكة تحجب hCaptcha | فشل فوري + `blocked_likely` | مرّر `NONECAP_HCAPTCHA_PROXY` |
| الخدمة معطّلة | قاطع مفتوح + `retry_after_seconds` | انتظر المدة أو راجع `/health/resilience` |
| تعلّق | مهلة → فشل صريح | ارفع `deadline_seconds` |
